# 2026-10-24 Phase 3 异常路径修复验收

本记录解决 [2026-10-22 提交前检查](2026-10-22-phase3-precommit-review.md)发现的三项阻塞，不改动已冻结的 Prompt、Schema、评测集或真实模型结果。本轮没有发起真实供应商调用。

## 修复边界

1. 真实模型 profile 在构造 HTTP 客户端时把 `model.timeout` 同时接入连接和读取超时。本地 300ms 慢响应配 50ms 超时，测试观察到 `MODEL_TIMEOUT`；其余请求形状及错误映射测试继续通过。
2. `V6__reserve_model_call.sql` 为每个分析建立唯一、已提交的调用占用记录。Worker 先短事务读取快照，再提交占用，然后在数据库事务外请求模型；用量单独提交，结果、状态、回执仍在同一短事务。后续结果或回执写入失败时，重投不会再次调用模型，而是落 `MODEL_CALL_OUTCOME_UNKNOWN` 并发往 DLQ。并发或短时间重投在超时窗口内延迟重试，避免抢先终结正在执行的调用。
3. 失败用量账本异常不再跳过 Worker 恢复。终态无法写入或 DLQ 无法确认时，监听器重新入队原消息，而不是在主队列没有 DLX 的情况下丢弃它；已占用的调用不会再请求供应商。

这是“至多一次供应商请求、失败时保守终结”的策略，不是供应商级 Exactly Once。若供应商已返回但数据库在记录用量之前不可用，已提交的占用记录仍证明本分析可能产生一次账单，但无法凭空恢复未持久化的精确 Token 数；此时必须人工核对供应商账单。已成功写入的用量独立于结果事务，结果回滚也不会删除它。
