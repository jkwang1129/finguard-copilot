# P4-3 调用与费用契约 v1

日期：2026-11-02。冻结时状态：作为P4-3实施输入，新增能力尚未实现。**当前实现与验收状态见[P4-3记录](../acceptance/2026-11-02-p4-3-governance.md)**，本契约约束保持不变。变更须新增版本和哈希，不能原地修改已投入运行的配置/价格。已有 V6 单次调用占用与当前安全护栏为必须保持的基线。

## 1. 执行单位与版本

每个 `analysisId` 最多一次付费供应商请求，不因 Outbox 重投、Worker 重启、Redis 租约过期或写结果失败重置。HTTP `202` 仍表示快照/运行/幂等键/Outbox 原子受理，不表示预算批准或分析成功。费用决策发生在 Worker 调用前；预算不足等决策进入受控失败终态，GET 返回状态及失败码。

调用前固化不可变运行清单，至少包括：

| 类别 | 必须关联的字段 |
| --- | --- |
| 身份与输入 | analysisId、服务端验证的审核员身份、任务 ID/版本、快照 SHA-256 |
| 模型 | 本地配置版本及内容 SHA-256、供应商、白名单端点 ID、模型 ID/别名、请求模式、输入/输出限制、超时、数据分类 |
| Prompt/输出 | 模板版本及实际文件 SHA-256、输出 Schema 版本及 SHA-256 |
| 知识与政策 | 已发布索引版本及成员清单 SHA-256、Embedding 版本、审定政策配置 SHA-256 |
| 费用与路由 | 价格表版本/内容 SHA-256/币种/生效范围、路由策略版本及 SHA-256、预算范围/额度、输入上界/输出上限、预计预留额、选择理由 |

版本名不能代替内容哈希。清单保存输入内容的校验和与受控标识，不保存 JWT、密钥、完整 Prompt 或动态事实正文。供应商模型别名不能证明底层权重不可变；可保存供应商返回的模型标识/指纹并标注可核验范围，不伪造权重哈希。

只有主模型 DeepSeek `deepseek-flash` 初始具备路由资格；具体配置仍须通过当前安全/质量验收。其余供应商保留候选状态，未通过同条件评测不得自动备用。无合格候选时拒绝调用，Stub 只用于显式开发模式，不冒充真实分析成功。

## 2. 金额与预留

- 初始内部预算币种 CNY；跨币种价格/预算不做隐式换汇。其他币种需独立版本契约。
- 金额用精确十进制，存储精度至少小数点后8位。预留按 `CEILING` 到8位向上取整；严禁 float/double 或先舍入 Token 单价。
- `reserved = ceil8(input_upper_bound × input_price_per_million / 1e6 + output_cap × output_price_per_million / 1e6)`；初始按输入缓存全部未命中、适用高峰价预留。不依赖未经证明的缓存命中折扣。
- 输入上界须由服务端对最终请求负载验证；仅有启发式 Token 估计不能作为严格费用上界。P4-3 必须补模型对应的 Token 计数或可论证的保守上界，并绑定相关版本；不能证明上界时拒绝真实请求。
- 明确分别限制每次分析、每个审核员/时间窗以及全局/供应商预算。各范围的已结算额、有效预留额及本次预留之和不得超过额度。
- 价格缺失、未定价、币种不匹配、版本/哈希不符、负价、失效价格不得进入真实调用。历史 `*-unpriced-v1` 不是零费用，也不改写为当前价格。

这些界限是应用在冻结价格与用量上界假设下的控制；供应商最终计费以账单为准。价格调整、非预期计费或响应缺少可用用量必须留下差异与核对状态，不宣称应用估算就是实际扣费。

## 3. MySQL 原子性与账本

MySQL 为预算/调用占用真相；Redis 不决定钱是否永久释放。P4-3 新表通过 V9 及后续迁移增加，V1–V8 不修改。

顺序：冻结清单并选候选 → 获取 Redis 配额/并发许可 → **一个 MySQL 事务**锁定预算范围并校验余额、写预算预留、取得已有的 `model_call_reservation` 唯一调用占用 → 提交 → 在期限/许可仍有效时发送一次 HTTP 请求。数据库故障时不发送。占用已存在时进入恢复判断，不能重新请求供应商。

预留状态至少具有以下含义：

| 状态 | 费用处理 | 后续调用 |
| --- | --- | --- |
| RESERVED | 已占预算，尚无可靠结算 | 同一分析不得再调用 |
| SETTLED | 有可靠用量，按本次价格结算，释放多余预留 | 不得再调用 |
| RELEASED_NOT_SENT | 能证明请求未发送，释放金额；保留不可重复调用占用 | 不自动重试或换供应商 |
| UNKNOWN_HELD | 可能已发送/计费，保留预留并进入核对队列 | 禁止重试、自动备用或按 TTL 释放 |

崩溃发生在占用提交后、HTTP 返回前，默认 UNKNOWN_HELD；不能凭“没有 SUCCESS 账本”推断未调用。供应商请求 ID、用量、失败码及核对事件独立记录。相同结算事件可幂等重放，不能重复计费或扣减。失败/超时/无效输出同样保留调用尝试；有真实用量的拒绝结果仍需结算。

当前 `model_usage_ledger` 的 ON DUPLICATE KEY UPDATE 不足以表达完整费用生命周期。实施时新增预算状态/核对事件，最终计费字段应幂等且不可随重投覆盖；修正通过追加调整事件表达。结果写入与费用写入失败不允许再次付费请求，保持 V6 已验证语义。

## 4. Redis 配额与租约

审核员身份只能来自 Core，不能取请求体；Key 不含 JWT、真实账户或高基数原始数据。配额、并发许可的获取/计数/释放采用原子操作，租约带持有者令牌，释放/续约须核对持有者，避免旧 Worker 释放新租约。

- Redis 故障、额度耗尽或无供应商许可：新请求 fail-closed；尚未发出模型请求时可进行有界的本地排队/消息恢复，不能绕过限制。
- 租约期限覆盖请求绝对期限及清理余量，发送前再核验期限/持有者；续约失败后不启动新的外部请求。
- 已在途请求不会因租约过期获得第二次调用资格；MySQL 调用占用继续防重。短期许可过期不释放 UNKNOWN_HELD 的钱。
- Redis 租约是并发治理机制，不声称在任意进程暂停或供应商异常下能精确统计所有外部在途请求；需记录许可丢失/超时并保守恢复。

## 5. 故障与降级

| 触发点 | 行为 |
| --- | --- |
| 无可用模型、预算不足、无有效价格/版本 | 不发请求，记录受控决策及终态 |
| Redis/DB 不可用且尚未取得付费调用资格 | 不发请求；有界恢复后仍失败则终态，不能无条件放行 |
| HTTP 超时、连接中断、响应解析失败、进程崩溃 | 可能已计费，UNKNOWN_HELD，不自动重试/备用 |
| 401/403/429/5xx 且无可靠用量/不计费证明 | 保留尝试及核对状态，不默认按0元结算 |
| 用量可信但 Schema/事实/政策拒绝 | 保存失败与用量，正常结算，不保存可用分析结果 |
| 模型返回后结果/用量数据库写入失败 | 保留调用占用及预留，恢复落库/核对，不重发模型 |
| 仅有旧存量结果 | 按当前恢复授权边界校验；无引用保守拒答可不访问知识服务；不新增付费调用 |

重试仅用于可证明不发起额外付费请求的本地操作，次数/期限有界。路由只在调用占用取得前选择一个合格候选；调用后失败不能切换供应商。Phase 5 多次模型交互须另立预算与调用序号契约。

## 6. 可验收门槛

以下是 P4-3 必须新增的实现测试，本文冻结不表示它们已通过：

1. 同分析并发/重投/Worker重启：供应商 HTTP 请求最多一次，费用与结算幂等。
2. 多分析竞争同一预算：所有事务下的预留总额不突破各级额度；十进制边界及向上取整正确。
3. 价格/Prompt/索引/政策版本错配或未定价：请求数0，留明确原因。
4. Redis 故障、额度耗尽、租约过期/误释放：不绕过配额，不重复调用，不释放未知费用。
5. 占用提交后的崩溃、网络超时、无效输出、账本/结果写入故障：预留不丢、未知状态可追踪、无自动备用。
6. 使用量完整/缺失/供应商修正账单分别演练：不把未知费用写0，不覆盖历史定价证据。
7. 正常主模型及无合格备用控制：路由理由可解释，安全护栏、Core只读、现有恢复语义继续通过。

## 7. 实施顺序与阶段边界

P4-3.1 运行清单/价格不可变版本 → P4-3.2 MySQL预算预留与结算 → P4-3.3 Redis配额/许可 → P4-3.4 单主模型路由与故障矩阵 → P4-3.5 合成真实链路验收。

真实 Embedding、大规模 RAG质量、真实人工校准、参考基线两项漏报、反馈保留期限、前端反馈验收仍在原阶段清单跟踪。本契约允许开始 P4-3 工程开发，不将这些未满足条件改写为已完成，也不启动 Phase 5 Tool Calling/Graph/MCP。
